=====================================================================
TEST 3 - VERIFICATION DES REGLES DE FILTRAGE
=====================================================================

REPONSE
Le pare-feu UFW est actif sur les 5 VM avec la politique "deny incoming"
(tout est bloque sauf ce qui est autorise explicitement) :

  VM1 : SSH, 80/tcp, 443/tcp, 53 (depuis les 3 sous-reseaux)
  VM2 et VM3 : SSH, 8080/tcp uniquement depuis VM1 (69.41.31.10)
  VM4 : SSH, 5432/tcp uniquement depuis VM2 (31.69.41.11) et VM3 (31.69.41.12)
  VM5 : SSH, 9090 et 3000/tcp uniquement depuis VM1 (41.69.31.10)

Principe : seul le proxy (VM1) atteint les applications, seules les
applications atteignent la base de donnees.

COMMENT TESTER
1. Afficher les regles sur chaque VM :
     sudo ufw status verbose
2. Ouvrir un port d'ecoute temporaire :
     VM4 : nc -l 5432      VM2 : nc -l 8080
3. Test BLOQUE (depuis VM5), attendu : timeout
     nc -zv -w 3 31.69.41.20 5432
     nc -zv -w 3 69.41.31.11 8080
4. Test AUTORISE, attendu : succeeded
     Depuis VM2 :  nc -zv -w 3 31.69.41.20 5432
     Depuis VM1 :  nc -zv -w 3 69.41.31.11 8080

A retenir : "timeout" = paquet bloque par le pare-feu ; "refused" =
paquet autorise mais aucun service n'ecoute.

RESULTAT : regles appliquees sur les 5 VM.

=====================================================================
TEST 5 - DEMONSTRATION D'UNE RESTAURATION DE SERVICE APRES INCIDENT SIMULE
=====================================================================

REPONSE
  - Panne d'un noeud applicatif : le load balancer (VM1) envoie tout le
    trafic vers l'autre noeud (tolerance de panne). Si un conteneur plante,
    Docker le redemarre (restart unless-stopped).
  - Perte de la base : restauration depuis la sauvegarde pg_dump.

COMMENT TESTER
Scenario A - arret d'un conteneur
  1. VM5 :  watch -n 1 curl -s -o /dev/null -w "%{http_code}\n" http://41.69.31.10
  2. VM2 :  sudo docker stop web
     Attendu : le code reste 200 (VM3 repond).
  3. VM2 :  sudo docker start web
     Attendu : VM2 revient dans le pool (curl alterne a nouveau).

Scenario B - arret complet d'une VM
  1. Eteindre VM2 depuis VMware.
  2. curl http://41.69.31.10 : le service repond toujours (VM3).
  3. Rallumer VM2 : retour a la normale.

Scenario C - perte de la base de donnees
  1. VM4 :  sudo -u postgres pg_dump appdb > /tmp/appdb.sql
  2. VM4 :  sudo -u postgres dropdb appdb        (incident simule)
  3. VM4 :  sudo -u postgres createdb appdb
            sudo -u postgres psql appdb < /tmp/appdb.sql
  4. Verifier que les donnees sont revenues.
