2. TOLERANCE AUX PANNES APPLICATIVE (SCENARIO A - PANNE D'UN NOEUD APPLICATIF)
--------------------------------------------------------------------------------
Objectif : Démontrer que si VM2 (`app1`) tombe en panne, le Load Balancer (VM1)
bascule automatiquement 100% du trafic sur VM3 (`app2`) sans interruption de service.

Etape 1 - Sur VM5 (192.168.38.105), lancer une surveillance continue en boucle :
[Où exécuter] : Sur VM5 (backup-sup)
[Commande]    :
  watch -n 1 'curl -s -o /dev/null -w "Code HTTP: %{http_code}\n" http://41.69.31.10'

Etape 2 - Sur VM2 (192.168.38.102), simuler une panne du service applicatif :
[Où exécuter] : Sur VM2 (app1)
[Commande]    :
  sudo systemctl stop africacloud
  sudo docker stop web 2>/dev/null

[Résultat attendu pendant la panne de VM2] :
  - Sur VM5, le code HTTP reste `200` (aucune coupure pour les utilisateurs).
  - Toutes les requêtes `curl http://41.69.31.10/api/health` sont servies par `VM3 (app2)`.

Etape 3 - Sur VM2 (192.168.38.102), rétablir le service :
[Où exécuter] : Sur VM2 (app1)
[Commande]    :
  sudo systemctl start africacloud
  sudo docker start web 2>/dev/null

[Résultat attendu après rétablissement] :
  - VM2 réintègre automatiquement le pool du Load Balancer Nginx sur VM1.
  - Les requêtes `curl http://41.69.31.10/api/health` alternent à nouveau entre `app1` et `app2`.

5. RESTAURATION AUTOMATIQUE DE LA BASE DE DONNEES APRES INCIDENT (SCENARIO C)
--------------------------------------------------------------------------------
A) Restauration automatique depuis VM5 vers VM4 (`restore_africacloud.sh`) :
[Où exécuter] : Sur VM5 (backup-sup - 192.168.38.105)
[Commandes]   :
  # 1. Lancer une sauvegarde fraîche sur VM5
  sudo /opt/africacloud/backup_africacloud.sh

  # 2. Simuler une perte totale des données sur VM4 (31.69.41.20)
  ssh -i /opt/africacloud/.ssh/id_ed25519 acadmin@31.69.41.20 "echo 'P@ssWord' | sudo -S python3 -c \"import sqlite3; c=sqlite3.connect('/opt/africacloud/africacloud.db'); c.execute('DELETE FROM issues'); c.commit()\""
  curl -s http://41.69.31.10/api/issues

  # 3. Restaurer la base de données centrale depuis VM5 vers VM4 en une commande
  sudo /opt/africacloud/restore_africacloud.sh
  curl -s http://41.69.31.10/api/issues

[Résultat attendu] :
  - Après l'étape 2, `curl http://41.69.31.10/api/issues` retourne `[]` (base vide suite à l'incident).
  - Après l'étape 3 (`sudo /opt/africacloud/restore_africacloud.sh`), la base de VM4 est restaurée depuis `/var/backups/africacloud/latest/vm4_db/africacloud.db` et tous les incidents réapparaissent immédiatement sur VM2 (`app1`) et VM3 (`app2`).
